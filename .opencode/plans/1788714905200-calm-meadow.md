# Guarded Forward Source Isolation

## Goal

Make nested custom-class forwards support the documented guard form:

```nix
guard = { config, ... }: _: lib.mkIf config.programs.git.enable;
```

The guard reads the final target configuration. Den guarantees this when the value is defined independently of the current forward. Self-dependent guards keep ordinary Nix recursion semantics; Den will not construct or subtract a pre-forward config snapshot.

## Implementation

1. Establish the regression boundary before changing production code.
   - In `templates/ci/modules/deadbugs/forward-module-metadata.nix`, retain both current enabled and disabled Git tests and keep `gitClass` identical to the documented example.
   - Expand the Git fixture with the load-bearing shape from the former Zed regression: register `gitClass` with `den._.host-aspects` through `den.default.includes`, include one environment aspect for the user, and let that aspect provide both the ordinary `homeManager.programs.git.enable` definition and a context-aware Git source module.
   - Make the Git source request `{ config, host, ... }`. Keep `settings.user.email = "root@linux.com"`, derive another valid Git setting through source-local `config`, and consume `host.name`. This keeps the test recognizable as the docs example while making source evaluation and Den context delivery observable.
   - Give both target fixtures an ordinary sibling Git setting and verify that it survives enabled and disabled forwarding.
   - Add exact assertions for leaked `_`, `_module`, `warnings`, `assertions`, `_type`, `condition`, and `content` keys. The context-aware source ensures the collision-validator metadata that exposed the Zed failure is present at the forwarding boundary.
   - Because `denTest` attrset comparisons are partial, compute exact leaked-key lists and list occurrence counts rather than relying on smaller expected attrsets.

1. Separate implicit nested-source evaluation from the target fixpoint in `nix/lib/forward.nix`.
   - Add an internal `sourceSpecialArgsFn` to the forward specification.
   - When `adaptArgs` is omitted, merge the target module's core arguments with `config._module.args`, then remove reserved `config`, `options`, and `lib`. The fresh source evaluator will provide its own reserved arguments while retaining ordinary arguments such as `pkgs`.
   - When `adaptArgs` is explicit, use its result verbatim. This preserves compatibility for `adaptArgs = lib.id` and for deliberate target-config access. Continue to recommend an alias such as `osConfig` when callers need target config without replacing source-local `config`.
   - Keep existing top-level forwarding and `extraArgsFor` behavior unchanged.

1. Replace `den.fwd` staging in `nix/lib/aspects/fx/handlers/forward.nix::mkAdapterAspect`.
   - Remove the staging include and `options.den.fwd.<adapterKey>` declaration from the nested complex-adapter branch.
   - Lazily evaluate `adapterMods ++ [ sourceModule ]` with `lib.evalModules` and `specialArgs = sourceSpecialArgsFn args`.
   - Pass `sourceModule` as a module instead of calling source functions. This preserves imports, module keys, priorities, defaults, Den context wrappers, and source-local module semantics.
   - Strip evaluator metadata from `evaluated.config` at the existing root and target-path boundaries.
   - Compute the dynamic target path once, nest the cleaned source with `lib.setAttrByPath`, and apply `guardFn args` to the complete nested module. The `mkIf` must stay at the target module boundary.
   - Remove now-unused `adapterKey` and `freeformMod` parameters from `mkAdapterAspect`, but keep `adapterKey` in the route specification for identity and deduplication.

1. Preserve one-owner route materialization in `nix/lib/aspects/fx/spawn-node.nix`.
   - Rename `declaresForwardOption` to `parentOwnsAdapterRoute` and `parentDeclaredKeys` to `parentOwnedKeys`.
   - Keep the current filtering behavior for nested complex adapters even though they no longer declare `den.fwd`: the parent and spawned folds must not both synthesize the same payload.
   - Update the comments to distinguish simple routes that can still declare `den.fwd` from nested complex routes that need single-owner materialization to prevent duplicate definitions.

1. Add compatibility and duplicate-sensitive coverage.
   - In `templates/ci/modules/public-api/dynamic-forward.nix`, characterize explicit `adaptArgs = lib.id` with a source that reads an independently defined target value through `config`; it must behave the same before and after the fix.
   - Keep `templates/ci/modules/public-api/guarded-forward.nix` in the required verification set because its implicit nested source requests `pkgs`; together with the expanded Git regression, it covers ordinary module arguments without adding a synthetic source-evaluator fixture.
   - In `templates/ci/modules/public-api/forward-from-custom-class.nix`, retain the existing `userEmail` assertion and make the nested source consume the documented `osConfig` alias.
   - In `templates/ci/modules/deadbugs/issue-642-host-aspects-custom-class.nix`, retain every test and add a mergeable list contribution whose occurrence count must be exactly one for the host-aspects and host-projection cases.
   - In `templates/ci/modules/deadbugs/issue-645-chained-forward-classes.nix`, retain every test and add a `programs.bash.shellOptions` marker whose occurrence count must be exactly one in both host-aspects shapes.
   - Update stale comments in those regression files from declaration ownership to synthesized-route ownership without removing their historical explanation.

1. Record the implemented contract.
   - Rewrite `docs/adapter-forward-guard-design.md` from an undecided snapshot/subtraction proposal to the implemented independent-source/final-target lifecycle, including the independent-value guard contract and explicit `adaptArgs` escape hatch.
   - In `docs/src/content/docs/guides/custom-classes.mdx`, clarify that config guards can read independently defined final target values, self-dependent guards have no snapshot semantics, omitted adaptation preserves source-local reserved arguments, and target config should normally be exposed under an alias such as `osConfig`.
   - Keep the valid `git.userEmail` compatibility example unchanged.

## Red Gate

Run the expanded Git tests before production edits. Their context-aware source-local `config` lookup is the decisive red signal; the original static Git cases may already pass because earlier metadata cleanup covered part of the failure.

If the expanded Git test unexpectedly passes, do not change `mkAdapterAspect` speculatively. Inspect the actual source arguments and reduce the missing downstream condition, likely an `adapterModule` or source-internal conditional. Claim the guarded-forward lifecycle fixed only after a representative case fails before the change and passes after it.
